# WTFPS v1.5 — Evidence-Based Engine + Real Easy/Nerd Modes (Design Spec)

> Approved design. The detailed implementation plans live in
> `docs/superpowers/plans/2026-06-10-wtfps-v1.5-phase1-engine.md`,
> `…-phase2-verdict-digest.md`, and `…-phase3-ui-modes.md`.

## Context

v1 ships a working pipeline, but two weaknesses must be fixed before starting the v2
roadmap (before/after compare):

1. **Easy/Nerd modes are fake.** The only difference is a single conditional in
   `src/App.tsx` that appends the `NerdView` tables in Nerd mode. Headline, tiles,
   findings, and digest are byte-identical across modes — the DESIGN.md contract
   (easy = plain/reassuring with one fix; nerd = dense and exact) was never implemented
   as content, only as "show extra tables".
2. **Detection guesses instead of proving.** All four detectors consume whole-log
   aggregates (avg, p95, flag density). Nothing is time-aligned: the engine never asks
   "what was the GPU/CPU doing *while* FPS was low". Per-core CPU data, frametime
   percentiles, VRAM capacity, and gameplay-vs-menu segmentation are all ignored, so the
   verdict — and the LLM digest built from it — cannot support its claims.

The fix is already in the data. Modern HWiNFO (7.63+, Sep 2023) **embeds Intel
PresentMon by default**: both sample-log families (Intel+NVIDIA, AMD+NVIDIA) contain
`GPU Busy / GPU Wait / CPU Busy / CPU Wait (avg) [ms]`, per-frame-derived
`Framerate Presented/Displayed (1% low / 0.1% low)`, `Frame Time Presented` percentiles,
per-core/thread usage and effective clocks, absolute VRAM MB columns, and a rich set of
latched limiter flags. v1 uses none of them. `GPU Wait` high while FPS is low *is* a
measured CPU bottleneck — no inference needed.

## Decisions (locked in interview)

| Topic | Decision |
|---|---|
| Evidence bar | Every finding carries an evidence grade: **`measured`** (Tier 1: PresentMon busy/wait, latched limiter flags, per-frame-derived lows) vs **`inferred`** (Tier 2: utilization heuristics). The grade is shown in UI and digest. When data is missing, the app says exactly which sensors to enable. |
| Non-gameplay time | **Auto-detect gameplay windows.** The log is cut into time windows; each is classified gameplay / idle / loading. All verdicts and stats come from gameplay windows only. Report coverage: "analyzed 14 min of gameplay out of a 22 min log". |
| Verdict shape | **Time-split + worst moments.** (a) "GPU-bound 71% of gameplay, CPU-bound 18%" from per-window classification; (b) forensics on the worst FPS-drop windows showing the time-aligned sensor state. Headline names the dominant limiter. |
| Easy/Nerd | **Different depth of the same story.** Easy: verdict sentence, time-split as a simple bar, ONE prioritized fix, friendly copy — no tables, no percentiles. Nerd: same verdict plus the full evidence chain — windowed timeline, worst-moment forensics, per-core grid, sensor table, evidence badges. |
| Root causes | All four in scope: thermal/power **collapse over the session** (heat-soak; validates undervolts), **VRAM overflow** stutter, **RAM/pagefile pressure** stutter, **single-thread CPU ceiling**. |
| Scope | One spec, three phased implementation plans (engine → verdict/digest → UI), each phase shippable on its own. |
| Inconclusive logs | **Honest + actionable.** Lead with "couldn't determine the bottleneck from this log", list what *was* ruled out, and give a checklist (PresentMon sensors, RTSS armed, 500–1000 ms polling). Never assert what HWiNFO cannot prove. |

## Evidence model

### Tier 1 — `measured`

Available when the PresentMon block is logged (default in HWiNFO 7.63+). Per window:

- `dev = (frameTime − gpuBusy) / frameTime`
  - `dev < 0.10` → **GPU-bound** … unless GPU power sits far below its limit with no
    power/thermal flags → **underutilized** (engine/driver pathology, *not* CPU-bound —
    the CapFrameX Starfield case).
  - `dev > 0.175` → **CPU/system-bound** (strengthened when `cpuBusy ≈ frameTime`).
  - between → **ambiguous** (say so).
- **Cap gate runs first.** Under an FPS cap, `CPU Busy ≈ frametime` even when the CPU
  idles — verified in our own sample (120 cap: CPU Busy 8.03 ms vs frametime 8.33 ms).
  A capped window is classified `capped` and busy-ratio logic is suppressed.
- Plausibility guard: PresentMon tracks one process and can pick the wrong one. If
  `gpuBusy > frameTime × 1.15` or FPS↔frametime disagree by >20%, demote the window to
  Tier 2 and note it.

### Tier 2 — `inferred`

Fallback when PresentMon columns are absent:

- Latched limiter flags (`Performance Limit - *`, `Thermal Throttling`,
  `Power Limit Exceeded`, AMD `Throttle Reason - *`) are **read-and-latched hardware
  reasons** — polling-rate-insensitive and therefore the strongest Tier-2 evidence.
- `GPU Core Load ≥ 97%` sustained across consecutive windows → GPU-bound (medium).
- `GPU Core Load ≤ 90%` + corroboration (`Max CPU/Thread Usage ≥ 95%` or
  `Performance Limit - Utilization` firing during gameplay) → CPU-bound (medium).
- The 90–97% band is genuinely ambiguous at 1–2 s polling — reported as ambiguous.

### Data hygiene rules

- RTSS `Framerate 1% Low` is frequently logged as **0 = not armed** → treat 0 as missing.
- Honest 1%/0.1% lows come only from per-frame-derived PresentMon columns. Percentiles
  of 2-second-averaged FPS systematically overstate lows → label those "p5 of sampled
  FPS", never "1% low".
- Use **effective clocks** (counter-averaged), never instant clocks, for throttle and
  collapse trends.
- Sanitize non-finite frametimes (`inf ms` appears in real logs).

### Never-assert list (HWiNFO cannot provide the evidence)

No analyzer exists for these; a guidance catalog phrases them as "can't measure this —
here's what would":

1. Background-process attribution (no per-process columns).
2. RAM speed/latency-boundness (no measurable signal).
3. Shader-compilation vs asset-streaming stutter (indistinguishable).
4. Sub-window stutter without per-frame-derived columns.
5. CPU-vs-GPU bound while an FPS cap is active (busy metrics distorted).

## Architecture

```
bytes ─▶ decode ─▶ parseCsv ─▶ buildColumns
      ─▶ normalize        (+timesMs, +CoreMatrix, +~18 new canonical keys)
      ─▶ buildFps         (+row-aligned series, +PresentMon/RTSS lows)
      ─▶ computeStats     (unchanged)
      ─▶ buildWindowAnalysis   src/windows/   NEW: grid → activity → limiter → split → worst
      ─▶ cause analyzers       src/causes/    NEW: replaces src/detect/, evidence-graded
      ─▶ buildVerdict     (time-split headline, primaryFix, guidance)
      ─▶ buildDigest      (coverage, time-split, worst moments, evidence tags)
```

`src/engine/analyze.ts` remains the single seam; `AnalysisResult` gains
`windows: WindowAnalysis`. Layering stays acyclic:
`types` ← `stats` ← `windows` ← `causes` ← `verdict`/`digest` ← `ui`.

Key structural choices:

- **Per-core data is a separate `CoreMatrix`** (row-aligned arrays with P/E/std core
  typing), *not* array-valued sensors — only two consumers (single-thread analyzer,
  nerd CoreGrid), so it stays out of the generic stats machinery. When the
  `Max CPU/Thread Usage` column is absent it is derived per-row from the matrix.
- **Windows are ~5 s** (4-sample floor at 2 s polling; `lowConfidence` single-window
  fallback for short logs). Window classification is a pure function
  `WindowMetrics → limiter`, making every rule a one-object table test.
- **Benchmark logs stay honest:** logs with no FPS (Cinebench) classify windows as
  "active workload", never worded as gameplay, and never get a gaming bottleneck verdict.
- **AMD GPU `Throttle Reason - Power/Thermal` map onto the same semantic flag keys** as
  NVIDIA's `Performance Limit - Power/Thermal`, so everything downstream is
  vendor-agnostic. dGPU/iGPU anchor disambiguation extends to the new VRAM and flag
  columns (verified collisions in both sample families).

## Root-cause analyzers (`src/causes/`)

| Analyzer | Evidence (strong) | Fate of v1 code |
|---|---|---|
| `cpuBound` | CPU-bound windows from classifier; single-thread ceiling = `Max CPU/Thread ≥ 95%` while total ≤ 60% inside those windows; CoreMatrix names the pinned thread ("P-core 2 T0") | Replaces `detect/cpuBottleneck.ts`; whole-log GPU-usage heuristic absorbed by Tier-2 window rule |
| `gpuBound` | GPU-bound windows subdivided by limiter-flag density → power / thermal / voltage / plain compute; reports `underutilized` pathology share | New |
| `thermalCollapse` | Epoch comparison (first 25% vs last 25% of gameplay windows): FPS ratio < 0.92 AND effective-clock ratio < 0.95 AND (late temp near session max OR rising flag density); linear-trend r² ≥ 0.3 guard rejects bimodal logs | Replaces the instant-clock-vs-peak heuristic in `detect/throttling.ts`; flag-count reporting kept, re-homed |
| `vramPressure` | `D3D Dedicated` p95 ≥ 90% of capacity (capacity = max of Allocated+Available) AND `D3D Dynamic` spill rising AND frametime spikes in the same windows; reports headroom MB | New |
| `ramPressure` | Existing p95 thresholds + upgrade: frametime spikes co-located with high-RAM windows → warn, else info | Carved out of `detect/powerHotspotRam.ts` |
| `fpsCap` | Existing logic + cap share from time-split | Moves nearly verbatim |
| `hotspotDelta` | Existing hotspot-delta + power-limit-density checks (hardware health, orthogonal to limiter) | Kept as-is, tagged `measured` |

## Easy vs Nerd content contract

| Element | Easy | Nerd |
|---|---|---|
| Headline | Time-split-phrased, friendly ("Mostly GPU-bound — that's the good kind of busy") + coverage line | Same verdict, exact numbers |
| Time split | `TimeSplitBar` — stacked CSS bar, legend, no numbers beyond percents | Same bar + `WindowTimeline` (FPS sparkline + per-window limiter band strip) |
| Findings | `PrimaryFix` — ONE card, one fix, plain words | Full findings list with `EvidenceBadge` (`measured`/`inferred`) per finding |
| Forensics | — | `WorstMoments` — up to 3 cards: timestamp, FPS drop %, mono snapshot of aligned sensors, fired flags |
| Per-core | — | `CoreGrid` — per-thread avg/max usage, P/E grouped |
| Tables | none | Existing SensorTable / FpsDetail / FlagTable |
| Guidance | `GuidanceCard` only when inconclusive | `GuidanceCard` always when data is missing |
| Digest/specs | unchanged, both modes | unchanged |

Fix priority ladder for `primaryFix`: thermal/power collapse > VRAM overflow >
dominant-limiter fix > cap headroom note.

All UI honors DESIGN.md: tokens only, numbers in `.mono` on solid surfaces, glass
untouched, no new chart library (SVG/CSS like the existing `UsageTimeline`).

## Digest additions (both modes; full mode gets the long form)

```
Gameplay coverage: analyzed 14.2 min of gameplay out of 18.5 min log (8 s windows)
Time split (gameplay only): GPU-bound 71% [measured], CPU-bound 18% [measured], ambiguous 11%
Frame times (PresentMon): avg 8.9 ms, p99 21.4 ms, 1% low 64 FPS (source: Frame Time Presented)
VRAM: D3D dedicated p95 7,410 MB of 8,188 MB (~780 MB headroom), dynamic spill flat
Worst moments:
- +8m12s: 31 FPS (−61%) — GPU Busy 31.8 ms ≈ frame time 32.1 ms, GPU 99%, Perf Limit - Power fired [measured]
Detected events:
- [warn] [measured] GPU-bound and power-limited for 64% of GPU-bound time …
Missing data that would sharpen this: …
Goal: …
```

Worst-moment lines reuse the same snapshot formatter as the UI — one source of truth,
no number drift.

## Definition of done (v1.5)

- All 12 sample logs analyze with no errors and no NaN, including all new `windows.*`
  fields.
- The capped sample (KaiC_NTE, 120 FPS cap) classifies as **capped**, not CPU-bound,
  despite `CPU Busy ≈ frametime`.
- Superposition logs classify GPU-bound with `measured` windows; Cinebench logs produce
  no gameplay-worded claims and surface guidance instead.
- Easy mode renders no tables or percentiles; Nerd mode shows the full evidence chain;
  every finding carries an evidence badge in Nerd mode and an evidence tag in the digest.
- Inconclusive logs lead with what was ruled out + the logging checklist.
- `npm run build` and `npm run test` green after every phase.

## Risks

1. **No real game log in `HWINFO samples/`** (all are Cinebench/Superposition runs) —
   segmentation thresholds are tuned on synthetics. Mitigated by coverage transparency
   and smoothing; capture a real gaming session (with menu time) before Phase 3 polish.
2. **PresentMon wrong-process** — per-window plausibility check demotes to Tier 2.
3. **TimeSplitBar palette** — DESIGN.md allows existing tokens only; `--accent` vs
   `--text-dim` may be too subtle for GPU-vs-CPU. Ship with existing tokens, revisit.
4. **All-AMD rigs untested** — AMD dGPU `Throttle Reason` anchor resolution has no
   sample; mapping kept, flagged for validation when a sample lands.
5. **2 s polling noise** — 4-sample window means are noisy; absorbed by the ambiguous
   band and the guidance push toward 500–1000 ms polling.
